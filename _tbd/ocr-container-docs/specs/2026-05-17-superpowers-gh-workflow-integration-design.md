# Superpowers ↔ GitHub Issues — unified workflow integration

**Date:** 2026-05-17
**Session:** `superpowers-gh-integration`
**Scope:** Workspace-wide. Extends and partially supersedes
[2026-05-09-github-issues-projects-design.md](2026-05-09-github-issues-projects-design.md)
and [2026-05-10-feature-request-spec-decomposition-design.md](2026-05-10-feature-request-spec-decomposition-design.md).

---

## 1. Goals & non-goals

### Goals

1. Make GH Issues the single execution surface — ship-issue picks from issues, not markdown roadmaps.
2. Keep `writing-plans` as the planning step — plan docs stay in-repo as the authoritative source of detail.
3. Make entry bidirectional: start from a GH issue *or* from a brainstorming session with no orphan work either way.
4. Replace the one-shot `decompose-spec` with an idempotent sync that keeps GH issues current as plans evolve.
5. Give every superpowers artifact type (decisions, specs, plans, tasks, research) a grooming path — automated for mechanical cases, CT-interactive for judgment calls.
6. Model ship-issue task context on executing-plans: the bot reads the plan section for full context, not just the GH issue title.

### Non-goals

1. No GitHub Projects board — `status:*` labels carry workflow state, same as today.
2. No multi-user ceremony or review gates beyond CT arming `bot:ship-issue-ready`.
3. No auto-execution of triage or spec-writing by the bot in v1 — all three remain CT-interactive.
4. No changes to bug or chore flows — `kind:bug` and `kind:chore` issues continue to be filed directly without a spec.

## 2. Four-level issue hierarchy

Every piece of work lives at one of four levels. Each level has a GH issue and a markdown artifact:

| Level | GH kind | Markdown artifact | Closed when |
|---|---|---|---|
| Decision | `kind:decision` | `docs/decisions/YYYY-MM-DD-slug.md` | Decision doc written |
| Spec | `kind:spec` | `docs/specs/YYYY-MM-DD-slug-design.md` | All child issues closed |
| Plan | — (no separate GH issue; plan doc links from spec issue body) | `docs/plans/YYYY-MM-DD-slug.md` | n/a — artifact only |
| Task | `kind:feature` / `kind:bug` / `kind:chore` | — (body populated from plan section) | PR merged |

Decisions and specs each have their own GH issue. Plans share the spec issue (the plan doc is a sibling artifact, not a new issue level). Tasks are the leaf tracking issues ship-issue picks up.

## 3. Issue body contracts

### Decision issue body
```
Decision: docs/decisions/YYYY-MM-DD-slug.md
Spawns: #N, #M   ← spec issues created from this decision
Status: open while deliberating; close when doc is written
```

### Spec issue body
```
Spec: docs/specs/YYYY-MM-DD-slug-design.md
Plan: docs/plans/YYYY-MM-DD-slug.md
Decision: #N        ← parent decision issue (if any)
Tracks: #N          ← parent feature-request (if any)
Milestone: spec: <slug> (#M)
```

### Task (child tracking) issue body — generated by `decompose-spec --sync`
```
Approach: <one sentence from plan task>
Blocked by: #N, #M
Plan: docs/plans/YYYY-MM-DD-slug.md#task-slug
Verification: <command>
Tracks: #N   ← parent spec issue
Acceptance:
- [ ] ...
- [ ] ...
```

The full task context (Context, detailed Approach, rationale) stays in the plan doc section.
ship-issue reads the GH card for routing and acceptance, then fetches the `Plan:` section for execution context.

For `model:haiku effort:S` tasks the body omits the Context block — lean card only.

## 4. Triage skill — two outcomes, no direct-ship shortcut

`/triage <N>` (feature-requests only; bugs and chores file direct):

```
kind:feature-request
    └─ /triage decides:
         ├─ Standard → fork kind:spec issue
         │               CT runs /spec-from-issue → plan → /decompose-spec --sync
         │
         └─ Architectural (affects multiple repos, implies a choice between
            fundamentally different approaches) → fork kind:decision issue
                → CT writes decision doc, closes decision issue
                → CT files one or more kind:spec issues from the decision
                → normal spec path from there
```

The size/effort decision moves inside `spec-from-issue` (short brainstorm for small features,
full session for large ones). Triage never routes to a direct-ship tracking issue for
feature-requests — every feature goes through at least a spec.

## 5. `decompose-spec --sync` — idempotent plan→GH sync

Replaces the existing one-shot `decompose-spec`. Can be run any time the plan doc changes.

```
/decompose-spec --sync <plan-path>
  (or)
/decompose-spec --sync <spec-issue-N>
```

### Algorithm

1. **Read plan doc** — extract ordered task list by `## Task N — <title> {#slug}` headings.
2. **Query GH milestone** — fetch all open + closed issues assigned to it (`gh issue list --milestone`).
3. **Diff by task slug** (stable ID from the `{#slug}` anchor; survives title renames):
   - Task in plan, no issue → **CREATE** issue with summary card body.
   - Task in plan, issue exists, body differs → **UPDATE** issue body.
   - Task in plan, issue was closed → **REOPEN** with comment "restored from plan update YYYY-MM-DD".
   - Issue exists, task removed from plan → **CLOSE** with comment "removed from plan YYYY-MM-DD".
4. **Resolve blockers** — for each `Blocked by: #task-slug` in plan, look up the corresponding
   GH issue number and write `Blocked by: #N` in the body.
5. **Ensure spec GH issue exists** — if none, create it with `Spec:` and `Plan:` body lines.
6. **Update plan frontmatter**:
   ```yaml
   synced: YYYY-MM-DD
   milestone: N
   ```

### Plan task format (required for sync to work)

```markdown
## Task 3 — Add bbox extraction  {#bbox-extraction}
model: sonnet  effort: M  area: backend

Context: ...
Approach: ...
Blocked by: #schema-definition
Verification: uv run pytest tests/test_bbox.py -v
Acceptance:
- [ ] ...
```

`{#slug}` is the stable identity key. `writing-plans` must emit this format for every task.

---

## 6. Plan doc frontmatter

Every plan doc gains a thin YAML frontmatter block:

```yaml
---
status: active | complete | archived
synced: YYYY-MM-DD
milestone: N
superseded-by: docs/plans/YYYY-MM-DD-new-slug.md   # optional
---
```

`decompose-spec --sync` writes `synced:` and `milestone:` after each run. The `status:` field
is managed by grooming (automated or CT).

## 7. Unified grooming system

### Automated (claude-bot scheduled job, no CT confirmation)

A `groom-auto` claude-bot job runs nightly via `coding-bot schedule`. It calls
`scripts/groom-auto.py` for the deterministic actions, then files a "Grooming report"
issue aggregating all judgment-required items.

**Deterministic actions (scripts/groom-auto.py):**

| Trigger | Action |
|---|---|
| Task `Blocked by:` issues all closed | Remove `status:blocked`, set `status:ready` |
| Milestone 100% closed | Set plan frontmatter `status: complete`, move to `plans/archived/` |
| All spec child issues closed | Close spec GH issue |
| Decision issue open + decision doc written | Close decision issue |
| Research file referenced by a spec or decision | Move to `research/archived/` |

**Report filing (claude-bot judgment):**
After running the deterministic script, the bot collects all flagged items and files
(or updates) a "Grooming report" issue in the workspace tracker repo with a structured
table of items needing CT review.

### Queued for CT (bot detects, queues into "Grooming report" GH issue)

| Signal | Type | Proposed action |
|---|---|---|
| Decision issue open, no decision doc written, >14 days | stale | Nudge CT |
| Spec issue open, no plan doc linked, >30 days | orphan | Write plan or close |
| Plan `synced:` >30 days, milestone <100% stalled | limbo | Keep / update / archive |
| Plan no `synced:` date (never decomposed) | orphan | Decompose or delete |
| Task `status:in-progress` >7 days, no recent PR activity | stalled | Requeue or close |
| Task `status:backlog` >90 days | limbo | Keep / reprioritize / close |
| Task `Plan:` link points to removed section | drift | Re-sync |
| Research file >180 days, not referenced anywhere | orphan | Delete or archive |
| Decision doc — all spawned specs fully shipped | complete | Archive doc |
| Decision doc — no spawned specs, >30 days | no-op decision | CT confirms intent |

### CT-interactive (`/groom`)

```
/groom decisions | specs | plans | tasks | research | all
```

Works through the queued report one item at a time (same interactive pattern as `/triage`).
CT decides: keep / update / archive / delete. Monthly recurring chore runs `/groom all`.

### One-time retroactive cleanup

`/plan-audit` — runs grooming detection across all existing `docs/plans/` files
and queues the backlog of stale ones. Intended as a one-time bootstrap run.

## 8. Bidirectional entry points

### GH-issue-first

```
CT files kind:feature-request
    → /triage → kind:spec issue (or kind:decision → … → kind:spec)
    → /spec-from-issue N
          runs brainstorming skill internally
          → spec doc + writing-plans → plan doc
          → /decompose-spec --sync → child task issues
    → CT arms bot:ship-issue-ready on ready tasks
    → ship-issue picks up
```

### Session-first

```
CT starts brainstorming session
    → brainstorming skill → spec doc
    → writing-plans skill → plan doc
    → /decompose-spec --sync
          → creates kind:spec GH issue (if none)
          → creates child task issues
    → CT arms bot:ship-issue-ready
    → ship-issue picks up
```

Both paths land at the same state: spec issue + plan doc + child task issues in GH.

## 9. ship-issue changes

ship-issue gains a two-step context read:

1. Read GH task issue body — routing (labels, blockers, milestone), acceptance criteria.
2. Follow `Plan: path#slug` link — read the plan task section for full execution context
   (Context, detailed Approach, Verification).

`ship-issue-pick.py` additions:
- Skip any issue where a `Blocked by: #N` issue is still open.
- Log `Plan:` path so the session can fetch it without a second GH query.

Haiku tasks (`model:haiku effort:S`) receive a trimmed body (no Context block) and are
batched into a single ship-issue session where practical (multiple small tasks per run).

## 10. Cross-repo work — skill convention

Any skill that encounters a needed change in a repo other than the one it is working in
**must not file or edit issues in the sibling repo autonomously**. Per-repo agents are
scoped to their own tree. Instead, the skill surfaces a formatted ready-to-run recommendation
for CT to review and execute.

### Standard cross-repo recommendation format

When a skill (brainstorming, spec-from-issue, decompose-spec, or a per-repo agent mid-task)
identifies a cross-repo gap, it emits a block like this before continuing:

```
Cross-repo recommendation
  Target: <repo>  (e.g. pdomain-book-tools)
  Reason: <one sentence — what's missing and why it belongs there>
  gh issue create -R ConcaveTrillion/<repo> \
    -l kind:feature-request -l status:backlog \
    --title "<title>" \
    --body "Tracks: (none yet)\nContext: <where this was discovered>\n\n<body>"
  → Run this? CT can edit before executing.
```

CT reviews and runs (or edits) the command. The skill does not wait — it continues its
primary task. CT decides whether to file the issue and when to triage it.

### Where this convention applies

| Skill | When to emit |
|---|---|
| `brainstorming` | When a design decision requires a sibling-repo change as a prerequisite |
| `spec-from-issue` | When writing the spec identifies upstream or sibling gaps |
| `decompose-spec --sync` | When a plan task targets a different repo |
| Per-repo agents (mid-task) | When implementing a task reveals a missing upstream capability |
| `/triage` | When a feature-request is better owned by a different repo |

### Cross-cutting work (spans multiple repos)

File the feature-request against the most-upstream affected repo (usually `pdomain-book-tools`).
Downstream repos get their own tracking issues when the upstream spec decomposes — the
upstream plan's tasks will emit cross-repo recommendations for each downstream piece.
